# Contributing to the docs

The site at <https://top-metal-solder-balls.readthedocs.io/> is built from
[`docs/`](docs/) with Sphinx and MyST. This file says how its pages are
written and what to run before merging a change.

## Who the pages are for

The reader has wafer.space die, or a tapeout coming, and wants to put solder
balls on them at home. They need to know which method to try first, what to
buy, and how to lay out the pads. Write every page for that person.

- Open each page by saying what the reader gets from it.
- Leave out how the research was done, who asked for it, and which document a
  fact was first seen in. Cite the source of a claim and stop there.
- Write so that someone outside the project understands the page on its own.
  Do not quote or attribute project discussions.

## Say what is true now

- A page describes the current state of knowledge. It does not say what an
  earlier draft said, what changed, or when it was written or last checked.
- Git holds the history. Put what changed and why in the commit message, not
  on the page. No "status as of" lines and no changelogs.
- Leave out options that have been ruled out, unless a reader would go
  looking for them. Then one sentence is enough.
- A date belongs on a page only when it is a fact about the world, such as
  when a run shipped. Write it as `YYYY-MM-DD`.

## Scope

- Home methods only: things that can be done with hobby tools. A wide process
  window and a high failure rate are acceptable, and parts only need to work
  from 0 °C to 50 °C. Anything that needs a wire bonder, a vacuum system or an
  outside service goes under `docs/industry/` as reference.
- GF180MCU is the target process, with aluminium top metal on the 11 kÅ
  stack. sky130 material is for comparison only.
- Describe non-open processes and products as "proprietary", not
  "commercial".

## Organise and link

- Every page belongs to one of the sidebar sections in
  [`docs/index.md`](docs/index.md).
- At the first mention on a page, link a method or term to its page on the
  site, a file to its place on GitHub, and a fact to its source. The reader
  should never have to search for what a sentence is talking about.
- Never guess a URL. If a page has gone, link an archived copy.
- Pages of the same kind use the same layout. A home method page has these
  sections in this order, leaving out any with nothing to say: the idea with
  its cross-section diagram, How it works, What to buy, Known problems and
  unknowns, Safety, Fit.

## Claims and sources

- A claim from a source carries a citation such as `[vt-thesis]`. Keys, URLs
  and descriptions live in [`docs/_links.md`](docs/_links.md), one per line.
  [`docs/update_links.py`](docs/update_links.py) copies the ones a page cites
  to the end of that page and rebuilds the Sources page.
- The pages were drafted by an AI model. Its own inferences are marked "my
  reasoning", and "I" on a page means that model.
- Mark anything measured on real die as measured. Until then, nothing is.
- Mark each price as listed or as a guess.

## Diagrams

- Every diagram is an SVG generated by
  [`docs/diagrams/gen.py`](docs/diagrams/gen.py). Change the script and rerun
  it. Do not edit the SVG files.
- Backgrounds are transparent. Labels must not overlap the drawing or each
  other.
- A diagram redrawn from a source says so in its caption, and says which
  numbers are estimates.

## Units and spelling

- Unit symbols with a space: 250 µm, 0.5 mm, 50 °C, 11 kÅ. Dimensions use ×.
- British spelling: aluminium, passivation, metallisation.
- Headings in sentence case, short enough for the sidebar.

## Before merging

```sh
python3 docs/diagrams/gen.py
python3 docs/update_links.py
sphinx-build -W -n -b html docs docs/_build/html
sphinx-build -b linkcheck docs docs/_build/linkcheck
```

The first three must be clean. Read the link check by hand: some sites answer
403 to any robot, which is not a broken link. Then open the built pages and
look at them, because problems such as overlapping labels and cut-off tables
only show when rendered.
